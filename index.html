Architecting a next-generation R&D data platform

How we moved an R&D centre from manual spreadsheets and file dumps to an automated data platform, without replacing a single spreadsheet.

This post walks through how we built a system that automatically collects, organizes, and analyzes research data that was previously buried in spreadsheets and shared drives. If you've ever struggled with messy shared folders and copy-paste reporting, the problems here will feel familiar; and you don't need an engineering background to follow along.

01 the problem

Operating in the dark ages of data management

Think of it this way
Imagine running a hospital where every patient record is a sticky note on someone's desk: no central filing, no backups, no way to search across patients. That was roughly the situation here, except the "patients" were experimental units and the "sticky notes" were spreadsheets.

Before this platform, every critical R&D decision flowed through a tangle of Google Sheets, offline Excel dumps, and manual chart-plotting sessions. The centre produced enormous volumes of workflow data at every stage, but none of it was searchable, connected, or versioned.

01
Google Sheets dependency

Process parameters for every stage of work lived in unstructured, manually-entered spreadsheets with no versioning or validation.

02
Data lake chaos

Time-series test data from machines was exported as .xlsx and synced to an offline Google Drive: no schema, no indexing, no structure to directories.

03
Manual analysis loop

Analysts manually opened hundreds of Excel files and plotted time-series graphs for every business-critical decision.

04
Organizational constraints

Proposals to migrate off Sheets or use direct network drives met consistent resistance. The platform had to work around the existing tools.

Why does this matter?
Every hour an analyst spent manually opening and charting spreadsheets was an hour not spent on actual R&D. Without a connected view of the data, tracing a defective unit back to the process that caused the issue was nearly impossible.

03 phase 1
Phase 01

The foundation: Tracking how work flows (Process lineage)

Why does this matter?
Without this, if a final product failed quality checks, there was no easy way to trace back through every stage it went through to find where things went wrong. Building a connected graph of every step was the key to making that possible.

Since replacing Google Sheets wasn't an option, we built a synchronisation engine instead. Every few hours, a Google Sheet Pusher script downloads fresh CSV snapshots, compares them against the previous version, and pushes only the delta into PostgreSQL.

Idempotency started at ingestion time. We kept consecutive versions of each CSV, hashed both, and only when those hashes diverged did we compute the set of mismatching process IDs and send targeted updates through the Django API. If a snapshot was unchanged, the poll became a no-op. That made scheduled syncs safe to rerun and prevented spreadsheet churn from becoming redundant database writes.

The schema mirrored the real workflow without forcing researchers to change how they worked. Each stage got its own table inheriting from BaseProcessModel, regex rules enforced identifier consistency on the source sheets, and a LineageEdge table connected every stage into a queryable DAG that could handle both splits and merges.

04 phase 2
Phase 02

Orchestrator: Making the file lake workable

Think of it this way
Think of this phase as building an intelligent mailroom for thousands of incoming packages (files). The mailroom knows which packages it has already opened, which ones are urgent, and can open multiple packages at once, all without losing track of anything.

To process the .xlsx files sitting in an offline synced Google Drive, we enforced a regex-based directory tree and a strict naming template for each analysis type. That turned a shapeless file dump into something the pipeline could actually search, classify, and reason about.

Idempotency by construction

The orchestrator used an SQLite job_status table as a ledger of every discovered file path, job type, and latest outcome. Each run first loaded the set of already-successful jobs, pulled a map of the unit IDs researchers were actively tracking, searched indexed paths for candidate files, and then filtered out any path that had already been marked successful for that job type. This made the system idempotent, safe reruns stopped being a convention and became the default behavior.

Failure handling and scheduling

The same ledger handled failure modes. Every attempt was upserted back into job_status with its status and logs, warnings were raised for misplaced files, and failed jobs remained eligible for later reprocessing instead of silently disappearing. A baseline qualification run acted as a gateway: downstream analysis jobs for a unit were only queued after that first qualification artifact was marked SUCCESSFUL.

The other piece that made the system usable was prioritization. Jobs were not processed FIFO: a weighted heapq priority queue scored work as recency_score × job_class_weight, so newer and more decision-critical files rose to the top first. Once queued, independent jobs were fanned out through ProcessPoolExecutor, which let us scale throughput without breaking ordering guarantees inside the dependency chain.

Deep dive: Why we converted files to Parquet
  • Cheaper downstream I/O: raw .xlsx parsing was expensive, repetitive, and full of workbook-level fluff we did not care about once a job had been understood, so after a successful run the orchestrator converted only the necessary columns into Parquet.
  • Column-oriented reads: because Parquet is built for efficient storage and retrieval, downstream routines could touch only the fields they needed instead of reparsing whole spreadsheets every time.
  • Cleaner plotting path: our delivery layer already relied on Apache Arrow, another columnar format optimized for fast scans and low-overhead transport, so serving processed series from Parquet into Arrow was a much cleaner route than going back to raw spreadsheets for every plot.
05 phase 3
Phase 03

Signal cleanup: separating spikes from real anomalies

What problem are we solving?
Sensor data is noisy. Imagine a heart monitor that occasionally shows a spike: is that a real cardiac event, or just the patient shifting in bed? We needed to automatically tell the difference in our time-series data, so researchers could focus on the events that actually mattered.

Most of the time-series processing itself was classified business logic, but one technical problem was reusable: distinguishing meaningless spikes from true anomalies in traces whose ideal shape should have been mostly monotonic.

Simple derivatives were too brittle, because local slope changes fired constantly even when the underlying profile was behaving normally. We also tried Savitzky-Golay smoothing, which helped with denoising but still did not reliably separate nuisance spikes from the events that actually mattered.

The heuristic that worked

The approach that finally held up was a layered heuristic. We first measured deviation inside a rolling window and flagged only windows whose deviation crossed a tuned threshold. Those candidate spike windows were then embedded into a 3D feature space built from the original trace axes plus the deviation signal, and clustered with DBSCAN, with careful tuning of eps (how close points need to be to form a cluster) and minPts (minimum number of points for a cluster). Dense regions of candidates usually corresponded to recurring spike behavior or measurement artifacts; candidates that failed to join any cluster were treated as the real anomalies worth escalating.

06 phase 4
Phase 04

Presentation layer: React + Express

What problem are we solving?
All the data processing in the world is useless if the results stay buried in files on a server. This phase turned invisible processed data into interactive charts and dashboards that researchers could actually use without freezing their browsers.

With data ingested and files processed into Parquet/Arrow formats, we built a web interface to replace manual plotting. An Express.js backend acts as a high-performance REST proxy and cache in front of Django, with a dedicated Python microservice that reads Parquet files and returns Arrow IPC data as Base64.

To prevent the UI from freezing when rendering charts with millions of data points, we implemented a Web Worker architecture: the worker receives Arrow Base64, decodes it, parses the Apache Arrow binary, transforms it into Plotly-ready JSON, and posts the traces back to the main thread, leaving the UI fully responsive throughout. Session-level caches reduced repeat fetches, and defensive UI boundaries ensured that a bad plot or malformed payload degraded locally instead of crashing the whole experience.

07 phase 5
Phase 05

Injecting AI: Natural-language queries and chat agents

The big idea
What if researchers could just type a question like "Which units failed the stress test last week?" and get an answer, without knowing anything about databases or writing any code?

The final evolution gave researchers the ability to query their data in plain English. We built an AI agent directly into the React frontend, backed by a Dual-Loop pipeline with a self-healing ActionReconciler to prevent hallucinated tool calls.

Deep dive: Benchmarking AI models before committing

We benchmarked the LLM providers and models we had access to before deciding where each one fit. A separate pytest-based NL2SQL harness ran structured query tasks across multiple models, checking not just whether they produced something plausible, but whether they returned parseable JSON, generated executable SQL, and matched validated reference behavior.

That benchmarking changed how we used models in practice. Faster and cheaper models made sense for narrow classification work, while stronger models were reserved for heavier generation tasks. Our validation was also intentionally a little fuzzy in the right places: if a model returned a superset of columns but the row count and row values still matched the correct answer, we treated that as acceptable because the information was still right. Just as importantly, the benchmark suite made failure modes visible early: some models rambled instead of returning structured JSON, some timed out, and some generated SQL that looked reasonable but failed execution or result validation.

The reconciler detects mismatches between the intent classifier's output and the main generator's proposed actions, then runs a targeted healing pass before the response reaches the user, significantly reducing erroneous tool invocations in production.

08 takeaways

Working with constraints, not against them

The core lesson: immovable organizational constraints aren't blockers — they're the design spec. Every layer of this platform was engineered around a fixed reality rather than an ideal one.

Constraint-first design

Hash-based CSV diffs and regex-constrained file discovery let us treat Sheets and Drive as pollable sources without forcing teams to abandon them.

Lineage as a first-class primitive

Modelling the workflow DAG explicitly in Postgres enabled traceability and cross-stage queries that were previously impossible.

Priority over FIFO

A recency-weighted queue plus parallel processing kept the most urgent jobs moving first without sacrificing safe reruns.

Heuristics over naive calculus

Rolling-window deviation plus DBSCAN worked better than simple derivatives when the goal was separating recurring spikes from true anomalies.

Benchmark before betting

A pytest-based benchmark suite told us which models were dependable for classification, generation, and NL2SQL, and which ones only looked convincing.

Self-healing agents

The Action Reconciler pattern: classify intent, generate, then verify; dramatically reduced hallucinated tool calls at the LLM layer.
