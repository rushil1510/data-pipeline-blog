Case Study  ·  OLA Electric, Bengaluru

Architecting a next-generation hardware R&D data platform

How we moved a hardware manufacturing R&D centre from manual spreadsheets to a fully automated, AI-augmented data ecosystem — without replacing a single spreadsheet.

Django · PostgreSQL Celery · Redis React · Express Apache Arrow NL2SQL · LLM Agents Google Drive API
01 the problem

Operating in the dark ages of data management

Before this platform, every critical manufacturing decision flowed through a tangle of Google Sheets, offline Excel dumps, and manual chart-plotting sessions. The centre produced enormous volumes of process data at each manufacturing stage — but none of it was searchable, connected, or versioned.

01
Google Sheets dependency

Process parameters for every manufacturing stage lived in unstructured, manually-entered spreadsheets with no versioning or validation.

02
Data lake chaos

Time-series test data from machines was exported as .xlsx and synced to an offline Google Drive — no schema, no indexing.

03
Manual analysis loop

Analysts manually opened Excel files and plotted Performance vs. Time graphs for every business-critical decision.

04
Organizational constraints

Proposals to migrate off Sheets or use direct network drives met consistent resistance. The platform had to work around the existing tools.

02 architecture overview

The complete platform ecosystem

Data flows from two immovable sources — Google Sheets and Google Drive — through ingestion services into a PostgreSQL backbone, then out through a Node.js layer to a React frontend and an AI chat agent.

03 phase 1
Phase 01

The foundation — manufacturing lineage DAG

Since replacing Google Sheets wasn't an option, we built a synchronisation engine instead. Every few hours, a Google Sheet Pusher script downloads CSV snapshots, hashes them against the stored version, and polls only the changed rows into PostgreSQL.

The core schema models every manufacturing stage as its own table, all inheriting from a shared BaseProcessModel. Because hardware units are born from splitting and combining materials, the data structure is a true DAG — a LineageEdge table connects nodes across stages.

04 phase 2
Phase 02

Orchestrator engine — taming the Drive

To process the physical .xlsx files in Google Drive, we enforced a regex-based file system tree and built an idempotent pipeline using an SQLite job index as the single source of truth.

The "Final Validation" cycle acts as a gateway: downstream test jobs for a unit are only queued after their validation job is marked SUCCESSFUL. Jobs aren't processed FIFO — a weighted priority queue using heapq sorts by recency_score × job_class_weight, ensuring the newest and most critical tests run first.

05 phase 3
Phase 03

Scaling with Celery — distributed testing pipeline

To gain proper observability, distinct worker nodes, and retry semantics, we migrated the legacy SQLite engine into a full Django + Celery application backed by PostgreSQL. Celery Beat triggers an ingestion task that queries the external API, checks the path index, creates job instances, and dispatches them through a TaskRouter to the appropriate worker queue.

06 phase 4
Phase 04

Presentation layer — React + Express

With data ingested and files processed into Parquet/Arrow formats, we built a web interface to replace manual plotting. An Express.js backend acts as a high-performance REST proxy and cache in front of Django, with a dedicated Python microservice that reads Parquet files and returns Arrow IPC data as Base64.

To prevent the UI from freezing when rendering charts with millions of data points, we implemented a Web Worker architecture: the worker receives Arrow Base64, decodes it, parses the Apache Arrow binary, transforms it into Plotly-ready JSON, and posts the traces back to the main thread — leaving the UI fully responsive throughout.

07 phase 5
Phase 05

Injecting AI — NL2SQL and chat agents

The final evolution gave researchers the ability to query their data in plain English. We built an AI agent directly into the React frontend, backed by a Dual-Loop pipeline with a self-healing ActionReconciler to prevent hallucinated tool calls.

The reconciler detects mismatches between the intent classifier's output and the main generator's proposed actions, then runs a targeted healing pass before the response reaches the user — significantly reducing erroneous tool invocations in production.

08 takeaways

Working with constraints, not against them

The core lesson: immovable organizational constraints aren't blockers — they're the design spec. Every layer of this platform was engineered around a fixed reality rather than an ideal one.

Constraint-first design

Polling ingestors and idempotent file discoverers let us treat Sheets and Drive as append-only sources without ever touching them.

Lineage as a first-class primitive

Modelling the manufacturing DAG explicitly in Postgres enabled traceability and cross-stage queries that were previously impossible.

Progressive evolution

SQLite → Celery → PostgreSQL allowed the pipeline to grow from a cron script into a distributed system without a big-bang rewrite.

Self-healing agents

The Action Reconciler pattern — classify intent, generate, then verify — dramatically reduced hallucinated tool calls at the LLM layer.
